# 定时签到基础奖励活动设计

## 背景

当前签到功能只有一套全局规则。状态查询和实际签到都会实时读取同一份配置，奖励由以下部分组成：

- 基础随机奖励档位；
- 昨日消费返利；
- 连续签到额外余额；
- 总奖励上限；
- 累计消费或充值资格门槛。

运营需要在指定的若干自然日启用另一套基础随机奖励，活动结束后自动恢复日常规则。活动不能改变消费返利、连续签到额外余额、资格门槛或总奖励上限。

## 已确认的产品决策

- 活动只覆盖基础随机奖励金额及其概率。
- 活动按北京时间自然日生效。
- 开始日期当天 `00:00` 生效，结束日期次日 `00:00` 失效。
- 多个已启用活动不允许日期重叠。
- 活动通过请求时规则解析自动生效和失效，不使用定时任务改写全局配置。
- 用户每天仍只能签到一次；规则切换不重置签到状态。
- 已经签到的奖励保留，不追补也不扣回。

## 目标

1. 保持现有日常签到配置为稳定的基础规则。
2. 支持管理员提前创建、审核并启用定时活动。
3. 活动开始和结束不依赖后台任务执行成功。
4. 保证签到状态展示与最终到账使用同一套规则解析语义。
5. 保留完整历史审计信息，能够解释每笔奖励来自哪套活动规则。

## 非目标

- 活动不覆盖消费返利配置。
- 活动不覆盖连续签到规则；连续签到继续直接发放额外余额。
- 活动不覆盖签到资格门槛或总奖励上限。
- 本期不支持周期性活动、按小时活动或重叠活动优先级。
- 本期不支持活动奖励与日常基础奖励叠加。

## 方案选择

### 采用：独立活动记录 + 请求时解析

日常配置继续使用现有设置。新增独立的签到基础奖励活动记录；每次查询状态或签到时，系统按北京时间日期解析唯一生效活动。若有活动，只替换日常配置中的基础奖励档位；否则完整使用日常规则。

该方案不依赖定时任务，因此服务重启或调度器停机不会造成活动漏开、漏关，也不会覆盖或丢失日常配置。

### 未采用：定时任务改写全局配置

该方式需要在开始时备份并覆盖全局配置、结束时恢复。任务漏执行、人工中途修改或服务故障都可能造成错误配置长期生效，审计也较困难。

### 未采用：逐日奖励日历

逐日保存奖励适合每天规则都不同的场景，但当前运营需求是按一段连续日期启用同一套规则，逐日配置会增加重复操作和出错概率。

## 数据模型

新增签到基础奖励活动实体，建议包含：

- `id`：活动 ID；
- `name`：活动名称；
- `status`：`draft`、`enabled`、`disabled`；
- `start_date`：北京时间开始日期；
- `end_date`：北京时间结束日期，包含当天；
- `reward_tiers`：完整的基础奖励金额、概率和排序快照；
- `created_by`、`updated_by`：管理员审计字段；
- `created_at`、`updated_at`：时间审计字段。

活动日期使用数据库日期类型，而不是浏览器或服务器本地时间戳。活动生效条件为：

```text
status = enabled
AND start_date <= current_beijing_date
AND end_date >= current_beijing_date
```

在签到记录中增加可空审计字段：

- `reward_campaign_id`；
- `reward_campaign_name`；
- `reward_campaign_tiers_snapshot`。

现有签到记录已经保存实际基础奖励、返利、连续签到奖励和最终奖励；新增活动字段用于解释规则来源，并防止未来活动修改影响历史审计。

## 规则解析与奖励计算

统一提供一个签到有效规则解析器：

1. 读取并校验日常签到规则；
2. 取得北京时间当天日期；
3. 查询当天唯一的已启用活动；
4. 若存在活动，将日常规则中的 `tiers` 替换为活动 `reward_tiers`；
5. 重新计算基础奖励预览和概率总和；
6. 保留日常规则的其他全部字段不变。

最终奖励仍按现有顺序计算：

1. 抽取基础随机奖励；
2. 计算昨日消费返利；
3. 计算连续签到额外余额；
4. 应用日常总奖励上限；
5. 保存奖励明细与活动快照。

状态查询和实际签到必须复用同一个解析器。实际发奖在事务内再次确认活动，避免跨北京时间零点或并发管理操作导致展示规则与到账规则不一致。

## 活动生命周期与约束

### 草稿

- 可以修改名称、日期和奖励档位；
- 不参与规则解析；
- 新建时默认复制当前日常基础奖励档位。

### 已启用

- 参与规则解析；
- 启用前要求概率总和严格等于 `100%`；
- 启用前检查与其他已启用活动不存在日期重叠；
- 活动进行中不允许直接修改日期或奖励档位；
- 可手动停用，停用后立即回退日常基础奖励。

### 已停用或已结束

- 不参与规则解析；
- 历史内容只读；
- 可以复制为新草稿，调整后再次启用。

日期重叠既要在服务层给出明确错误，也要在数据库事务中通过锁定相关活动记录后重新检查，防止两个管理员并发启用重叠活动。

## 管理端 API

建议提供独立的管理接口：

- 获取活动列表及状态筛选；
- 获取活动详情；
- 创建草稿；
- 更新草稿；
- 启用活动；
- 停用活动；
- 复制活动；
- 删除未启用且无历史引用的草稿。

启用失败时返回结构化错误，至少区分：

- 日期范围非法；
- 奖励档位非法；
- 概率总和不等于 `100%`；
- 日期与现有活动冲突；
- 活动状态不允许当前操作。

## 管理端界面

在“签到管理”中增加“定时活动”区域：

- 列表展示名称、日期范围、状态、最低奖励、最高奖励和平均奖励；
- 支持进行中、即将开始、已结束、草稿和已停用筛选；
- 支持新建、编辑、复制、启用、停用和查看；
- 编辑器沿用日常基础奖励档位交互；
- 实时展示概率总和、最低奖励、最高奖励和平均奖励；
- 启用前显示最终日期范围和奖励摘要；
- 日期冲突时显示冲突活动名称与日期；
- 进行中活动提供明确的停用确认。

用户签到状态及后台签到记录增加活动来源展示：

- 是否使用活动规则；
- 活动名称；
- 实际基础奖励；
- 消费返利；
- 连续签到额外奖励；
- 最终到账金额。

## 错误处理与一致性

- 活动查询或数据校验失败时，签到应失败并记录明确错误，不能静默采用错误金额。
- 当天没有活动时才正常回退日常规则。
- 活动启用、停用和实际签到都使用事务保护。
- 同一用户同一天仍依靠现有唯一约束保证只发放一次奖励。
- 活动切换不修改已有签到记录。
- 手动停用进行中活动后，新签到立即使用日常基础奖励；停用前已签到用户保留原奖励。

## 测试范围

### 服务与仓储

- 没有活动时使用日常规则；
- 开始日和结束日使用活动基础奖励；
- 结束次日恢复日常基础奖励；
- 草稿和已停用活动不生效；
- 活动仅替换基础随机奖励；
- 消费返利、连续签到奖励、资格门槛和总奖励上限保持日常配置；
- 概率校验和日期校验；
- 重叠活动无法启用；
- 并发启用仍不能产生重叠活动；
- 跨北京时间零点重新解析规则；
- 并发签到仍只发一次奖励；
- 历史签到保存活动审计快照。

### API 与前端

- 活动增删改查和生命周期操作；
- 结构化错误展示；
- 列表状态和奖励预览；
- 进行中活动不可直接编辑；
- 停用确认和即时回退提示；
- 签到记录正确展示奖励组成和活动来源。

## 上线与兼容

- 数据库迁移只新增活动表及签到记录可空字段，不改变现有记录语义。
- 未创建活动时，生产行为与当前签到功能完全一致。
- 先上线数据库与后端，再上线管理界面；功能可通过没有已启用活动保持无影响状态。
- 上线后先创建一个短期测试草稿，验证启用、解析、停用和回退，再配置正式活动。
