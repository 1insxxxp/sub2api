# 自定义分组安全删除设计

## 背景

线上删除日志表明，自定义分组仍被 API 密钥使用时，删除接口会返回 `409 CUSTOM_GROUP_IN_USE`。用户解除密钥绑定后可以成功删除，因此故障并非数据库删除失败，而是现有界面没有展示绑定数量，也没有提供继续处理的路径。

## 目标

- 保留对误删正在使用分组的保护。
- 用户明确确认后，可以一次完成密钥解绑和自定义分组删除。
- 解绑与删除必须在同一个数据库事务中完成，不能留下部分成功状态。
- 被解绑的 API 密钥继续使用自身原分组，不失效、不改变原分组。
- 兼容旧前端：不带强制参数的删除请求继续返回冲突，不静默改变密钥。

## 方案比较

### 方案一：只改善错误提示

继续阻止删除，提示用户前往 API 密钥页逐个解除绑定。实现简单，但操作路径长，仍容易让用户认为删除功能不可用。

### 方案二：点击删除立即自动解绑

一次请求直接解绑并删除。操作最短，但用户不知道哪些密钥会被修改，存在误操作风险。

### 方案三：预检冲突后二次确认（采用）

首次删除保持现有保护，并在冲突元数据中返回绑定密钥数量。前端展示明确的二次确认；用户确认后发出强制删除请求。后端在单个事务中清空这些 API 密钥的 `custom_group_id`，再软删除自定义分组。

## API 与数据流

1. 前端发送 `DELETE /api/v1/custom-groups/:id`。
2. 服务端读取该用户拥有的分组并统计未删除 API 密钥的绑定数量。
3. 数量大于零时返回 `409 CUSTOM_GROUP_IN_USE`，元数据包含 `bound_api_key_count`。
4. 前端提示：继续删除会让这些密钥恢复使用原分组。
5. 用户确认后发送 `DELETE /api/v1/custom-groups/:id?force=true`。
6. repository 在同一事务中锁定自定义分组、清空其关联 API 密钥的 `custom_group_id`，再将分组标记为已删除和禁用。
7. 响应返回 `deleted: true` 与 `unbound_api_key_count`，前端刷新列表并提示成功。

## 并发与安全

- 强制删除事务锁定目标自定义分组，确保所有权和未删除状态在事务内再次校验。
- 解绑条件同时限定 `custom_group_id` 和未删除 API 密钥；删除期间新绑定需要遵循同一数据库约束/锁顺序，避免删除后残留绑定。
- 普通删除仍保持预检保护，旧客户端行为不变。
- 强制删除只清空自定义分组字段，不修改 API 密钥原分组、状态、额度或其他限制。

## 前端交互

- 第一次确认仍询问是否删除该分组。
- 收到 `CUSTOM_GROUP_IN_USE` 后，读取 `bound_api_key_count`，展示第二次危险确认。
- 第二次提示明确说明受影响密钥数量，以及密钥将恢复使用原分组。
- 用户取消时不做任何修改；强制删除失败时显示服务端错误。

## 测试

- Service：普通删除有绑定时返回带数量的冲突；无绑定时正常删除；强制删除调用原子 repository 操作。
- Repository：强制删除同时解绑所有未删除密钥并软删除分组；不影响其他分组和已删除密钥；所有权错误不修改数据。
- Handler：解析 `force=true`，冲突响应包含元数据，成功响应包含解绑数量。
- Frontend：普通删除成功、绑定冲突后二次确认、取消二次确认、强制删除成功和失败。
