# 邀请链接注册锁定设计

## 背景

当前邀请返利链接通过注册页 URL 中的 `aff` / `aff_code` 参数传递邀请码。前端会把邀请码写入 `localStorage`，并在注册页的可编辑输入框中展示；邮箱注册、邮箱验证和第三方 OAuth 最终仍把原始 `aff_code` 交给后端。后端使用客户端提交值绑定邀请关系。

因此，单纯隐藏输入框只能改善界面，不能阻止用户通过开发者工具、请求重放或修改浏览器存储替换邀请码。

本设计只处理“邀请返利码”（`aff_code`），不改变用于限制注册的一次性邀请码（`invitation_code`）、注册优惠码或现有返利计算逻辑。

## 目标

- 直接访问注册页时，继续显示可手动填写的邀请返利码输入框。
- 通过有效邀请链接进入时，隐藏输入框，但注册流程仍携带并绑定该邀请码。
- 有效链接建立服务端可信的邀请锁，客户端修改请求体中的 `aff_code` 无效。
- 同一浏览器最后一次打开的有效邀请链接覆盖之前的有效邀请链接。
- 无效链接不建立邀请锁，也不覆盖已有有效邀请锁；没有已有锁时显示手动输入框并允许改填。
- 邮箱注册、邮箱验证以及 Linux DO、微信、OIDC、GitHub、Google、钉钉第三方注册采用相同规则。
- 注册或登录流程完成后清理临时邀请状态。

## 非目标与限制

- 不修改返利比例、资格判断、充值返利、奖励领取或计费逻辑。
- 不把一次性注册邀请码与邀请返利码合并。
- 不阻止用户主动打开另一个有效邀请链接；这是已确认的“最后一次有效链接覆盖”规则。
- 浏览器所有者可以清除 Cookie、使用无痕窗口或更换设备。服务端无法在不引入侵入式设备指纹的情况下证明该浏览器此前访问过邀请链接。本设计保证当前正常注册流程中的不可见与不可篡改，不声称跨浏览器绝对锁定。

## 方案比较

### 方案 A：仅前端隐藏

根据 URL 是否存在 `aff` 参数隐藏输入框，继续提交原始 `aff_code`。

优点是改动小；缺点是客户端可以直接修改请求，无法满足防篡改要求，因此不采用。

### 方案 B：服务端签名邀请锁（采用）

新增公开解析接口。后端验证邀请码后签发 HttpOnly、SameSite=Lax 的签名 Cookie；注册与 OAuth 流程以该 Cookie 为权威来源。

优点是无需数据库迁移，部署简单，可复用现有 JWT/HMAC 密钥体系，并能跨邮箱验证和 OAuth 回调保持状态。缺点是用户清除 Cookie 后无法继续识别此前访问记录，但这属于已声明的浏览器边界。

### 方案 C：数据库注册意向

为每次邀请访问创建数据库记录，并通过随机令牌关联浏览器。

优点是便于审计、吊销和统计；缺点是需要迁移、过期清理、并发覆盖规则和额外运维，对当前需求过重，因此不采用。

## 架构与数据流

### 1. 邀请链接解析

注册页检测到 `aff` 或 `aff_code` 后，请求新的公开邀请解析接口。接口执行：

1. 规范化邀请码。
2. 检查邀请返利功能是否开启。
3. 验证邀请码对应有效邀请人。
4. 生成带版本、邀请人标识、邀请码、签发时间和过期时间的签名邀请令牌。
5. 通过安全 Cookie 写入浏览器；生产环境启用 `Secure`，统一使用 `HttpOnly`、`SameSite=Lax` 和 30 天有效期。
6. 只返回 `valid`、`locked` 等非敏感状态，不向页面返回可用于改写锁的签名密钥或内部信息。

只有验证成功才覆盖已有 Cookie。无效链接不得删除或覆盖一个仍有效的邀请锁。

### 2. 注册页状态

注册页加载时查询当前邀请锁状态：

- 存在有效服务端邀请锁：隐藏手动输入框，内部状态标记为 locked。
- 不存在邀请锁：保留当前可编辑输入框。
- URL 邀请码无效且没有已有锁：显示“邀请链接无效，请重新填写邀请码”，输入框保持可用。
- URL 邀请码无效但已有有效锁：保留原锁，不允许无效链接破坏已有归属。

前端不得把锁定邀请码放进可编辑表单状态，也不得依赖 `localStorage` 作为权威来源。现有本地缓存可以保留一段兼容迁移期，但只能辅助恢复界面，不能覆盖服务端锁。

### 3. 邮箱注册与邮箱验证

注册处理器先读取并验证签名邀请 Cookie：

- Cookie 有效时，服务端邀请码覆盖请求体中的 `aff_code`。
- Cookie 缺失或无效时，继续接受当前手动输入的 `aff_code`，保持直接注册兼容。

进入邮箱验证页时无需在 `sessionStorage` 保存锁定邀请码。最终注册请求仍由后端读取 Cookie；手动输入邀请码继续按现有流程保存与提交。

### 4. 第三方 OAuth

所有 OAuth 启动、待完成注册和回调流程统一使用邀请锁解析结果：

- 启动 OAuth 时优先采用有效的服务端邀请锁，而不是客户端提交的 `aff_code`。
- 需要跨跳转保存时，把签名后的邀请上下文放入现有 OAuth pending session/state，而不是保存可篡改的原始值。
- OAuth 新建用户时将已验证的邀请码交给现有 `BindInviterByCode` 流程。
- 已有账号登录或绑定第三方身份时不新建邀请关系。

### 5. 清理与覆盖

- 打开新的有效邀请链接：覆盖当前邀请锁，刷新 30 天有效期。
- 打开无效邀请链接：不改变当前有效锁。
- 注册成功：清理邀请 Cookie 与兼容本地缓存。
- 已有用户登录成功：清理临时邀请状态，不绑定邀请人。
- 签名错误、版本不支持或过期：视为无锁，清理无效 Cookie。

## 安全规则

- 签名使用现有服务端密钥派生独立用途密钥，加入固定 domain separation，避免与登录 JWT 混用语义。
- 采用恒定时间签名比较。
- Cookie 不包含密码、邮箱或其他注册信息。
- 后端不得信任前端的 locked 标志。
- 邀请锁存在时，请求体携带不同 `aff_code` 必须被忽略并留下安全审计信息；不得静默改写服务端锁。
- 解析接口沿用公开认证接口的速率限制，防止批量枚举邀请码。
- 错误响应不泄露邀请人邮箱、用户 ID 或邀请码存在性的额外内部信息。

## 错误处理

- 无效邀请链接：页面提示后允许手动填写，不阻断正常注册。
- 解析接口暂时不可用：不删除已有锁；没有已有锁时显示输入框并允许稍后重试。
- Cookie 失效：回退到直接注册行为。
- 注册过程中邀请绑定失败：保持当前注册成功优先的兼容语义，但记录结构化日志，便于排查返利归属失败。

## 测试范围

### 后端

- 有效邀请码签发签名 Cookie。
- 无效邀请码不签发、不覆盖已有有效 Cookie。
- 第二个有效邀请码覆盖第一个。
- Cookie 篡改、过期和错误版本被拒绝。
- 有效锁优先于请求体中的不同 `aff_code`。
- 无锁时手动 `aff_code` 保持兼容。
- 注册和已有用户登录完成后的清理行为。
- OAuth pending session/state 使用服务端已验证邀请上下文。

### 前端

- 直接访问注册页显示可编辑输入框。
- 有效邀请链接解析后隐藏输入框。
- 无效链接显示错误并保留输入框。
- 已有锁遇到无效链接时仍保持隐藏与原归属。
- 最后一次有效链接更新锁定状态。
- 邮箱验证跳转不丢失邀请关系。
- 各 OAuth 按钮不再以可编辑表单值覆盖邀请锁。

### 集成回归

- 邮箱直接注册、邮箱验证注册以及所有已启用 OAuth 提供商。
- 邀请返利关闭时不建立锁。
- `invitation_code` 与 `promo_code` 的既有行为不受影响。
- 移动端注册页在隐藏输入框后保持正常间距和可访问性。

## 发布兼容性

该方案不需要数据库迁移。蓝绿部署期间，新前端可能访问旧后端，或旧前端访问新后端，因此：

- 新前端在解析接口不存在时必须回退到现有可编辑输入框，不能阻断注册。
- 新后端继续支持旧前端提交原始 `aff_code`；只有存在有效邀请锁时才以锁为准。
- 待新版本稳定后再评估是否移除旧的本地缓存兼容路径。
