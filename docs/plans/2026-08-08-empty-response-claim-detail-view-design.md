# 空回申请独立详情入口设计

## 背景

管理员目前只能在待审核记录的“审批/驳回”弹窗中查看完整结构化请求信息。已补偿、已驳回等不可审批状态没有入口，只能看到列表摘要，无法追溯单条申请。

## 方案比较

1. **复用现有审核弹窗并增加只读模式（采用）**：所有状态展示同一套请求、计费和证据信息；待审核记录仍保留独立审批按钮。改动小，桌面与移动端样式不会分叉。
2. 新建第二个详情弹窗：查看与审批职责更独立，但会重复维护字段、翻译和移动端布局。
3. 新建详情路由：适合复杂审计工作台，但当前信息量不足以支撑独立页面，且会打断列表操作。

用户已批准方案 1。

## 交互设计

- 移动卡片和桌面表格的每条申请都显示“查看详情”。
- 点击后复用 `EmptyResponseClaimReviewDialog`，以 `view` 模式打开。
- 只读模式展示请求 ID、用量时间、模型、用户、分组、账号、Token、费用、请求/计费类型、端点、耗时、响应证据、用户原因、补偿来源和审核结果。
- 只读模式隐藏备注输入框和确认提交按钮，只保留“关闭”。
- 待审核记录继续显示“审批”和“驳回”；已完成记录只显示“查看详情”。
- 移动端继续使用可滚动底部弹窗，桌面端保持宽弹窗。

## 数据与安全

不增加后端接口和字段，继续使用列表 API 已返回的隐私安全结构化数据。不得展示提示词、响应正文、工具参数、完整 API 密钥或账号凭证。

## 测试

- 先增加失败用例，验证已补偿记录存在详情入口并可打开只读弹窗。
- 验证只读弹窗显示请求信息，且不存在文本框和提交按钮。
- 验证待审核记录的审批/驳回流程保持不变。
- 运行组件测试、语言键校验、类型检查和生产构建。
