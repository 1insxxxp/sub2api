# 抽奖活动页面设计

## 目标

新增一个面向所有已登录用户的抽奖页面，并由系统设置控制是否开放。系统只维护一个全局活动，后台可以配置活动规则和奖品；用户抽奖后，余额奖品自动入账，自定义产品奖品直接展示/发送给用户，并在页面查看历史记录。

## 已确认范围

- 仅支持一个全局抽奖活动，不支持多个活动并行。
- 参与者为所有已登录用户。
- 管理员可以在系统设置中开启或关闭抽奖功能。
- 后台控制每个用户的抽奖次数，支持两种活动次数模式：
  - 每日次数：每天按站点时区重置，每位用户每天可抽固定次数。
  - 总次数：活动期间每位用户共可抽固定次数。
- 奖品类型只有两种：余额、自定义产品。
- 余额奖品使用现有余额入账/流水能力自动发放。
- 自定义产品由后台维护奖品内容库存，一条内容对应一次中奖；内容可以是兑换码、链接或其他交付文本，中奖后只返回给中奖用户并写入其历史记录。
- 用户页面展示活动说明、剩余次数、抽奖入口、中奖结果和历史记录。
- 活动关闭、未开始、已结束、次数用尽或自定义产品库存耗尽时，用户不能继续抽奖，并得到明确提示。

## 方案选择

### 方案 A：所有规则和奖品放在系统设置 JSON 中

实现速度快，但奖品库存、并发扣减、历史查询和后台编辑都会依赖大 JSON，难以保证兑换码只发给一个用户，也不利于审计和后续扩展。

### 方案 B：活动、奖品、库存、抽奖记录独立建模（推荐）

使用独立数据表保存活动配置、奖品权重、产品内容库存和每次抽奖记录；系统设置只保存总开关。抽奖在数据库事务内完成次数校验、随机选奖、库存占用和奖励发放，可靠性和可追溯性最好，且仍然只维护一条活动记录。

### 方案 C：复用兑换码表，将抽奖当成特殊兑换码批次

可以复用部分兑换码能力，但抽奖需要权重、随机结果、次数限制和用户中奖历史，和现有兑换码生命周期并不完全一致，最终仍需要额外的抽奖记录与库存状态，边界反而更复杂。

采用方案 B。系统设置负责“能不能看到/参与”，抽奖领域表负责活动业务数据，余额奖励继续调用现有余额流水服务。

## 功能设计

### 管理端

在系统设置的“功能开关”中增加“抽奖”开关。关闭时：

- 用户端不显示抽奖导航入口。
- 用户直接访问抽奖页面或调用用户抽奖 API 时按功能关闭处理。
- 管理员仍可进入配置页面编辑活动。

开启时提供“配置抽奖活动”入口，进入独立管理页面。管理页面包含：

- 活动名称、活动说明。
- 开始时间、结束时间；为空表示不限制对应边界。
- 次数模式：每日次数 / 活动总次数。
- 每位用户可抽次数，必须为正整数。
- 奖品列表：奖品名称、奖品类型、权重。
- 余额奖品：余额金额，必须大于 0。
- 自定义产品奖品：产品说明和库存内容编辑框，按行录入内容；保存时忽略空行，一行代表一个可发放内容。
- 奖品启用/停用状态。

同一时间只允许一条活动处于启用状态。保存或启用活动时校验：活动至少有一个启用奖品；所有权重为正数；余额金额合法；自定义产品奖品有可用库存。停用活动不删除历史记录和已发放内容。

### 用户端

新增 `/lottery` 页面，放入用户导航；导航是否显示由公开设置中的抽奖开关控制，设置尚未加载时沿用项目现有的缓存/默认策略避免页面闪烁。

页面分为三部分：

- 活动区：显示活动名称、说明、活动时间、次数模式和剩余次数。
- 抽奖区：一个明确的抽奖按钮；请求期间禁用，结果以结果面板展示。余额中奖显示到账金额，自定义产品中奖显示产品名称和交付内容，并提供复制操作。
- 历史区：按时间倒序分页显示抽奖时间、活动名称、奖品名称、奖励类型、余额金额或已发放产品内容。

页面需要适配手机端，抽奖按钮和中奖结果保持稳定布局；活动未开放、未开始、已结束、次数用尽、奖品库存不足等状态都使用空态/提示状态，不显示不可操作的按钮。

## 数据模型

建议新增以下 Ent schema 和对应 migration。字段名以现有项目命名规范为准，金额使用 PostgreSQL `decimal(20,8)`，时间使用 `timestamptz`。

### `lottery_activities`

- `id`
- `name`
- `description`
- `status`：draft、active、disabled、ended
- `attempt_mode`：daily、total
- `attempt_limit`
- `starts_at`、`ends_at`，可空
- `created_by`
- `created_at`、`updated_at`

通过唯一约束/索引保证最多一条 active 活动；历史活动保留，便于历史记录回看。

### `lottery_prizes`

- `id`
- `activity_id`
- `name`
- `type`：balance、product
- `weight`：正整数或正数
- `balance_amount`，余额类型使用
- `description`
- `enabled`
- `sort_order`
- `created_at`、`updated_at`

### `lottery_prize_items`

- `id`
- `prize_id`
- `content`：兑换码、链接或其他交付文本
- `status`：available、claimed
- `claimed_by`、`claimed_at`
- `created_at`

自定义产品每次中奖占用一条 `available` 内容。占用使用行锁，确保同一条内容不会发放给多个用户。

### `lottery_draws`

- `id`
- `activity_id`
- `user_id`
- `prize_id`
- `prize_name`、`prize_type`：保存中奖快照，防止后台改名后历史记录失真
- `balance_amount`，可空
- `product_content`，可空
- `attempt_key`/幂等键
- `created_at`

抽奖记录是用户历史的唯一来源。中奖结果写入快照，避免奖品后续被编辑或删除后用户看不到已获得内容。

## 后端接口与数据流

用户接口建议注册在现有 `/api/v1` 用户路由下：

- `GET /lottery/activity`：返回当前可见活动、规则、奖品展示信息、当前用户剩余次数；不返回其他库存内容。
- `POST /lottery/draw`：执行一次抽奖，接收幂等键；返回中奖奖品、自动入账结果或自定义产品内容，以及剩余次数。
- `GET /lottery/history`：返回当前用户分页历史，支持按时间倒序查询。

管理员接口建议放在 `/api/v1/admin/lottery`：

- `GET /activity`
- `PUT /activity`
- `POST /activity/enable`
- `POST /activity/disable`
- `GET /prize-items`（按奖品查询库存状态）

抽奖事务流程：

1. 校验系统开关、登录用户、活动状态和时间窗口。
2. 对活动/用户次数范围加锁，计算当前模式下已使用次数；超过限制直接返回“次数已用尽”。
3. 根据启用奖品权重生成随机结果。对自定义产品奖品锁定并占用一条可用库存；如果抽中库存已空的奖品，则在事务内重新抽取可用奖品，所有产品库存都空时返回明确错误且不消耗次数。
4. 创建一条抽奖记录并消耗一次次数。
5. 余额奖品在同一事务中调用已有余额入账与流水逻辑；产品奖品把占用的内容写入抽奖记录并在响应中返回。
6. 提交事务后返回结果。重复幂等键直接返回第一次结果，不重复发放余额或产品。

随机与并发要求：服务端随机，不能由前端决定奖品；奖品结果、次数消耗和奖励发放必须以数据库事务为边界。管理端删除/修改奖品时不得破坏已有抽奖记录。

## 设置与导航集成

新增一个数据库设置键，例如 `lottery_enabled`，默认关闭，避免新功能在未配置活动时突然对外开放。管理员设置响应和公开设置响应都需要携带该开关；用户端只使用公开设置，不读取管理员设置接口。

前端沿用现有 `FeatureFlags`/公开设置注册机制：

- `frontend/src/stores/adminSettings.ts` 保存管理员设置页的状态与缓存。
- `frontend/src/views/admin/SettingsView.vue` 增加抽奖功能开关和配置入口。
- `frontend/src/components/layout/AppSidebar.vue` 增加带 feature flag 的“抽奖”用户导航项。
- `frontend/src/router/index.ts` 增加需要登录的 `/lottery` 路由，并在功能关闭时阻止直接访问。
- 增加 `frontend/src/api/lottery.ts`、用户页面、管理页面及中英文翻译。

后端设置服务需要提供读取抽奖开关的方法，并在公开设置序列化时只暴露布尔开关，不暴露后台奖品内容和兑换码库存。

## 错误处理

- 功能关闭或没有可用活动：用户端显示不可参与状态，接口返回稳定的业务错误码。
- 未开始/已结束：展示活动时间，不允许抽奖。
- 次数用尽：显示剩余次数为 0，不重复请求。
- 自定义产品库存不足：后台保存和启用时校验；并发耗尽时由后端返回“奖品已发完”，前端提示刷新活动。
- 余额入账失败或数据库事务失败：整个抽奖事务回滚，不能出现扣了次数但没有奖励的情况。
- 网络重试/重复点击：使用幂等键返回原结果，客户端同时在请求期间禁用按钮。
- 任何产品内容只返回给中奖用户的接口响应和其本人历史，不进入公开设置、活动摘要或其他用户接口。

## 测试策略

后端：

- migration/Ent schema 的表、索引、约束检查。
- 每日模式和总次数模式的边界测试，包括时区、活动窗口和并发请求。
- 加权随机结果可测试候选集过滤和随机注入，不依赖不稳定的概率断言。
- 余额奖品自动入账、产品库存单次占用、活动记录快照和重复幂等键测试。
- 功能开关关闭时的用户接口与管理员接口权限测试。

前端：

- API 类型和错误映射测试。
- 用户页面加载、剩余次数、抽奖中禁用、余额/产品结果和历史分页测试。
- 设置开关保存后导航显示/隐藏与直接访问守卫测试。
- 管理页面表单校验、奖品增删、产品内容按行解析和移动端布局测试。

验收标准：管理员关闭开关时普通用户看不到入口且不能调用抽奖；打开并发布活动后，任意登录用户能够在次数范围内抽奖；余额立即入账并有流水；自定义产品内容只发给中奖用户且不会重复发放；刷新页面后剩余次数、结果和历史记录保持一致。
