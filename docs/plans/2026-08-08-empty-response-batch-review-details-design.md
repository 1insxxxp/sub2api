# 空回批量审核详情设计

## 背景

当前批量审核弹窗只接收选中申请中的第一条记录。弹窗虽然展示选中数量与预计总补偿，但详细证据、用户、模型和请求信息始终来自第一条申请，管理员无法在提交前核对其他选中项。

## 方案比较

1. **只展示第一条代表记录**：界面最简单，但容易让管理员误以为所有选中项内容一致，审批风险最高。
2. **一次展开全部完整详情**：信息完整，但选择十几条后弹窗极长，移动端尤其难用。
3. **紧凑清单并逐条展开（采用）**：默认展示全部选中项的用户、模型、分组、账号、预计补偿和证据摘要；点击任意一项展开其完整结构化详情。兼顾可审查性和移动端可用性。

## 交互设计

- 单条查看与单条审批保持现有布局不变。
- 批量审批弹窗顶部继续显示选中数量和预计总补偿。
- 批量模式下用可滚动的折叠清单替代单条详情区域，并默认展开第一条。
- 每个清单项固定展示编号、模型、用户、分组、账号、预计补偿、申请原因和证据状态。
- 展开后展示请求 ID、调用时间、Token、计费、端点、耗时、结构化输出证据、用户说明和隐私提示。
- 桌面端弹窗适当加宽；移动端保持底部弹层，每条详情在弹窗内部滚动，不产生横向溢出。
- 统一审核备注和确认按钮作用于全部选中申请，不改变现有批量接口与失败项保留逻辑。

## 数据流

- 父组件从 `selectedIDs` 和 `claimCache` 派生有序的 `selectedClaims`。
- 批量弹窗新增 `claims` 属性；单条模式继续使用现有 `claim` 属性。
- 弹窗内部维护展开 ID 集合，批量弹窗每次打开时重置并默认展开第一条。
- 结构化详情提取为复用模板，避免单条和批量模式出现字段差异。

## 测试

- 批量弹窗收到并展示全部选中申请，而不是只展示第一条。
- 默认第一条展开，点击第二条后显示其完整请求证据。
- 单条查看和审批仍只展示一条，现有按钮和校验不变。
- 大量选中项使用有高度上限的纵向滚动容器，移动端无横向溢出。
- 批量提交仍使用原有全部选中 ID。
