# 酒馆综合月卡自定义分组设计

## 背景与目标

当前订阅套餐、用户订阅和 API 密钥都绑定单个分组。不同酒馆渠道因为成本和售价不同，被配置在不同来源分组中，因此用户若要同时使用多个酒馆渠道，需要创建多把 Key 或购买多份订阅。

本功能在“分组管理”中增加系统级自定义路由分组。管理员可以从多个来源分组中手动导入模型，创建“酒馆综合月卡”分组；套餐和 API Key 只绑定这个月卡分组，用户便能用一把 Key 调用其中所有模型。所有请求共享同一份日额度和月额度，但每次请求仍继承实际来源分组的渠道、模型和实时价格。

## 已确认的产品规则

- 管理员在分组管理中创建系统级自定义分组，不复用用户自行创建的私有自定义分组。
- 管理员选择多个来源分组，并从中逐个选择要纳入月卡的模型。
- 一把绑定月卡分组的 Key 可以调用所有已纳入模型。
- 所有来源渠道共享月卡的一份日额度和月额度。
- 额度用尽后直接拒绝请求，不使用用户余额继续消费。
- 用户通过明确的对外模型名选择渠道；系统不在同名渠道间静默负载均衡。
- 请求调度和成本计算使用来源分组；订阅鉴权和额度累计使用月卡分组。
- 来源分组价格调整后，新请求自动按新价格累计月卡用量，无需重新导入。

## 方案选择

### 方案一：把所有酒馆账号合并到一个普通分组

实现简单，但会丢失来源分组之间的独立定价与配置，后续需要复制账号、模型和倍率配置，维护成本高且容易产生价格偏差，因此不采用。

### 方案二：扩展现有用户自定义分组

现有用户自定义分组已经支持“对外模型名 → 来源分组/来源模型”路由，但它是用户私有资源，而且当前认证链路会把这类 Key 当作余额 Key，无法直接承载系统销售的共享订阅。强行复用会混合用户权限与平台商品配置，因此不采用。

### 方案三：系统级自定义路由分组

在普通分组和用户私有自定义分组之外，增加管理员维护的系统级自定义路由分组。它本身作为订阅售卖和额度归属分组，同时把具体请求路由到既有来源分组。该方案能保留每个渠道的定价、账号池和调度能力，并让一个订阅统一管理额度，因此采用此方案。

## 领域模型

系统级自定义路由分组仍以现有 `Group` 作为套餐、订阅和 API Key 的绑定对象，并增加明确的分组类型或能力标识，避免改变普通分组的行为。

新增系统路由模型配置，至少包含：

- 月卡分组 ID
- 对外模型名 `public_model`
- 来源分组 ID `source_group_id`
- 来源模型名 `source_model`
- 启用状态
- 创建和更新时间

月卡分组内的 `public_model` 必须唯一；同一来源分组和来源模型也不能被重复导入。来源分组继续持有账号池、平台、倍率、模型定价和调度配置，月卡分组不复制这些配置。

现有用户私有自定义分组及其数据表保持不变，避免影响已经创建的用户 Key。

## 管理端交互

管理员在分组管理中新建分组时选择“自定义路由分组”，然后：

1. 选择一个或多个来源分组。
2. 系统读取这些来源分组当前可用的模型并展示导入预览。
3. 管理员勾选需要纳入的模型，也可以修改其对外模型名。
4. 系统校验模型名冲突、来源分组状态和模型有效性。
5. 校验通过后一次性保存分组与全部路由。

导入采用快照方式。来源分组将来新增模型时，不会自动对月卡用户开放。管理员可以点击“同步模型”查看新增、失效和冲突项，再确认是否更新：

- 新增模型默认不勾选。
- 来源中已删除的模型标记为失效，并建议禁用对应路由。
- 来源价格变化只展示最新价格，不修改路由，因为请求会实时继承来源价格。
- 所有变更在确认后使用事务一次性保存，避免出现部分同步。

## 模型重名规则

目前各酒馆来源分组的模型名互不重复，首次导入时保持原模型名，不强制增加前缀。

如果以后出现不同来源分组包含相同模型名：

- 已上线的路由保留原对外模型名。
- 新导入的重名模型必须设置不同别名，界面建议使用 `模型名@来源分组简称`。
- 导入预览明确标记冲突；冲突未解决时禁止保存。
- 系统不自动合并、不覆盖已有路由，也不根据同名模型静默切换渠道。

这样既保持现有调用方稳定，也确保用户选择的模型能够唯一确定来源渠道。

## 请求链路与计费

请求上下文需要同时保留两个分组概念：

- 计费分组：酒馆综合月卡分组，用于订阅资格、日/月额度和套餐限制。
- 来源分组：路由命中的实际渠道分组，用于平台适配、账号调度、价格、倍率和成本控制。

完整流程如下：

1. API Key 认证并加载绑定的月卡分组和有效用户订阅。
2. 检查订阅有效期、日额度和月额度；任一额度不足即拒绝请求。
3. 根据请求中的对外模型名查找唯一的系统模型路由。
4. 把请求模型转换为来源模型，并使用来源分组执行账号调度和上游请求。
5. 使用来源分组当前生效的模型价格、倍率和实际 token/请求用量计算 `actual_cost`。
6. 将 `actual_cost` 累加到原月卡订阅的日用量和月用量，不扣用户余额。
7. 用量日志同时记录计费分组、来源分组、对外模型名和实际来源模型名。

已有普通订阅、余额 Key、用户私有自定义分组和 Composite 平台路由继续走原有链路。

## 错误处理与安全边界

- 月卡或日额度用尽：返回明确的额度不足错误，不回退余额。
- 对外模型不存在或被禁用：返回“模型不在当前月卡可用范围内”。
- 来源分组停用、来源模型被删除或无可用账号：返回“模型暂不可用”，不切换到其他来源。
- 来源价格缺失或无法计算：请求失败并记录运维告警，禁止按零价格计费。
- 路由重名或重复导入：管理端保存失败并指出具体冲突模型。
- 非管理员不能创建、编辑或同步系统自定义分组；购买用户不能修改路由。
- 路由更新需使相关 API Key 和分组缓存失效，避免旧路由长期驻留。

## 日志与可观测性

用量记录保留 `group_id` 作为月卡计费分组，并新增或补充来源分组字段。日志至少能回答：用户购买了哪个月卡、调用了哪个对外模型、实际进入哪个来源分组和来源模型、按什么实际成本扣减额度。

运维监控分别统计月卡分组的销售/额度使用和来源分组的请求/成本/故障，避免综合月卡掩盖单个来源渠道的问题。

## 测试策略

后端单元与集成测试覆盖：

- 分组类型和系统路由的创建、更新、唯一性及权限校验。
- 多来源模型导入、快照同步、删除模型和重名别名处理。
- 一把 Key 分别调用两个来源分组，且都累计到同一用户订阅。
- 来源分组价格不同或后来调价时，月卡额度按实际来源实时价格累计。
- 日/月额度耗尽后拒绝请求，且不扣用户余额。
- 来源停用、模型删除、缺少价格和无可用账号时关闭式失败。
- 普通分组、现有订阅和用户私有自定义分组行为不回归。

前端测试覆盖分组类型选择、来源分组选择、模型导入预览、模型勾选、别名编辑、冲突拦截、同步预览和错误提示。

## 上线方案

数据库变更只新增类型/路由能力和必要日志字段，不迁移或改写现有分组。部署后先创建内部可见的“酒馆综合月卡”分组与测试套餐，用内部账号验证跨渠道路由、共享额度、实时定价、日志归属及异常拦截。

验证通过后再开放正式套餐。若需要回滚，先停止销售并禁用月卡分组；既有普通分组和原有用户自定义分组不受影响。
