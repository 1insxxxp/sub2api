# 兑换失败限流时长修复设计

## 背景

线上兑换服务将“每小时最多 20 次失败”作为业务策略，但 Redis 仓储层把失败计数键的 TTL 设置为 24 小时，并且每次失败都会刷新该 TTL。活动兑换码集中发放后，用户反复提交已使用或同批次不可重复的兑换码，达到阈值后会被持续阻断约 24 小时；限流检查发生在兑换码查询前，因此有效兑换码也无法使用。

## 已确认处理

线上达到阈值的 17 个 Redis 限流键已经在备份后精准删除，未修改兑换码、余额或订单数据。

## 方案比较

### 方案一：将仓储层 TTL 修正为 1 小时（采用）

把 `redeemRateLimitDuration` 从 `24 * time.Hour` 改为 `time.Hour`，保留现有阈值、失败计数范围、Redis 错误降级和滑动窗口行为。改动最小，直接恢复代码注释与业务命名承诺。

### 方案二：导出服务层策略常量并由仓储层引用

可以避免两处常量再次不一致，但会让仓储层依赖服务层的策略细节，并扩大本次修复范围。当前仓储层已经依赖服务接口，但为单一 TTL 引入导出 API 没有必要。

### 方案三：将阈值和 TTL 配置化

灵活性最高，但需要配置、校验、默认值、部署文档和管理界面支持，不适合本次线上缺陷的最小修复。

## 数据流与错误处理

失败兑换继续通过 `IncrementRedeemAttemptCount` 对用户键计数并设置过期时间。达到 20 次后继续返回 `REDEEM_RATE_LIMITED`；Redis 不可用时仍保持 fail-open，不阻塞兑换。唯一行为变化是失败窗口由错误的 24 小时恢复为 1 小时。

## 测试

在仓储层 unit 测试中新增明确策略断言：`redeemRateLimitDuration == time.Hour`。先在旧实现上确认测试因得到 24 小时而失败，再修改常量并运行仓储层兑换缓存测试、相关服务测试以及后端格式检查。
