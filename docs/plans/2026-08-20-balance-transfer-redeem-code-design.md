# 余额转兑换码功能设计

## 背景

需要允许后台指定的部分用户，把自己账户内的余额转换成兑换码，并发送给其他用户使用。生成时必须立即扣减生成者余额，避免凭空增发额度。

## 目标

- 后台可以为指定用户开启或关闭“余额转兑换码”权限。
- 有权限的用户可以在用户端生成余额兑换码。
- 生成兑换码时，从生成者账户余额中原子扣除同等金额。
- 其他用户可以通过现有兑换入口使用该兑换码并获得余额。
- 系统能审计兑换码由谁生成、谁兑换、何时生成、何时兑换。
- 用户生成的转赠码不触发邀请返佣，避免余额被返佣机制放大。

## 非目标

- 不支持并发数、订阅时长等其他额度类型的用户自助转赠。
- 不支持一个兑换码被多人使用。
- 不在本次实现每日限额、审批流或批量生成。
- 不改变管理员现有生成兑换码的行为。

## 推荐方案

采用“用户表权限开关 + 兑换码来源审计”的方式。

### 数据模型

用户表新增布尔字段：

- `balance_redeem_code_enabled`: 是否允许该用户把余额转换为兑换码，默认 `false`。

兑换码表新增审计字段：

- `created_by`: 兑换码生成者用户 ID，可为空。管理员生成的历史码为空。
- `source`: 兑换码来源，默认 `admin`。用户余额转赠码使用 `user_balance_transfer`。

保留现有 `type = balance` 行为，这样兑换逻辑和前端展示仍然兼容现有余额兑换码。

### 后端流程

新增用户端接口：

- `POST /api/v1/redeem/generate`
  - 参数：`amount`，`expires_in_days` 可选，`notes` 可选。
  - 仅允许已登录且 `balance_redeem_code_enabled = true` 的用户访问。
  - 金额必须大于 0。
  - 在同一个事务中完成余额扣减和兑换码创建。
  - 余额不足时不创建兑换码。
  - 返回新生成的兑换码。

- `GET /api/v1/redeem/generated`
  - 返回当前用户生成过的转赠码列表。
  - 包含 code、value、status、created_at、expires_at、used_at、used_by 等必要信息。

生成逻辑：

1. 读取当前用户并检查状态与权限。
2. 校验金额、过期时间。
3. 使用现有原子余额调整能力扣除用户余额。
4. 创建 `type = balance`、`source = user_balance_transfer`、`created_by = 当前用户` 的兑换码。
5. 提交事务。
6. 失效生成者余额相关缓存。

兑换逻辑：

- 继续走现有 `/redeem` 流程。
- 当兑换码 `source = user_balance_transfer` 时，跳过邀请返佣。
- 其他管理员生成的余额码保持现有返佣行为。

### 管理端

在管理员用户创建和编辑表单中增加：

- `允许生成余额兑换码`

在管理员兑换码列表中展示或筛选：

- 来源 `source`
- 生成者 `created_by`

### 用户端

在现有 `/redeem` 页面增加一个仅授权用户可见的区域：

- 当前余额展示。
- 生成金额输入。
- 过期天数选择，默认 30 天。
- 生成按钮。
- 生成成功后展示兑换码和复制按钮。
- 展示自己生成过的兑换码列表，便于查看是否已被使用。

### 风险和边界

- 余额扣减和兑换码创建必须在一个事务中完成，避免扣款成功但没有生成码。
- 生成者和兑换者可以是同一个人，但业务上没有收益，只是余额转出再转回。
- 如果兑换码过期未使用，本次不自动退回余额。后续如需要，可以新增“过期转赠码退回”任务或人工处理能力。
- 用户生成的转赠码必须跳过返佣，否则会造成余额膨胀。

## 测试计划

- 未授权用户调用生成接口返回权限错误。
- 授权用户余额不足时返回余额不足，且不创建兑换码。
- 授权用户生成成功后余额减少、兑换码创建成功。
- 生成和扣款在事务中保持一致。
- 其他用户兑换转赠码后余额增加，兑换码状态变为已使用。
- 转赠码兑换不触发邀请返佣。
- 管理端可以开启或关闭用户权限。
- 用户端仅在有权限时展示生成入口。
