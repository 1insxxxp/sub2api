# 自定义分组失效来源修复设计

## 背景

线上普通分组采用软删除。`user_custom_group_models.source_group_id` 虽然有外键，但软删除不会触发外键约束，因此普通分组下架后，既有自定义分组仍可能保留指向该来源分组的模型映射。

当前运行时会过滤或拒绝这些映射：模型列表中对应模型静默消失，直接调用则无法解析来源分组。线上已发现 29 条失效映射，涉及 13 个自定义分组和 10 个仍在使用的 API 密钥。

## 目标

1. 防止管理员继续删除仍被有效自定义分组引用的来源分组。
2. 在用户编辑自定义分组时保留并明确展示失效映射，而不是静默隐藏。
3. 用户可从仍有权限的候选来源中重新选择并保存。
4. 网关仍不得调度失效来源，避免错误路由或错误计费。
5. 不自动改绑现有映射，避免跨分组价格、权限和平台语义被错误替换。

## 后端设计

### 删除保护

管理员删除普通分组前，查询未删除自定义分组中的来源引用数。引用数大于零时返回业务冲突 `CUSTOM_GROUP_SOURCE_IN_USE`（HTTP 409），并包含安全的引用数量；不泄露用户或模型明细。

检查必须位于 service 删除流程中，而不是仅放在 handler，确保所有删除入口行为一致。Repository 新增只读计数方法。

### 失效状态透出

自定义分组的模型 DTO 增加只读字段：

- `source_available`: 来源分组存在、未删除、启用且用户仍有权限时为 `true`。
- `source_issue`: 不可用原因的稳定枚举，例如 `source_group_unavailable` 或 `source_group_not_allowed`。

列表和详情接口继续返回原始映射，并根据当前来源状态填充上述字段。创建、更新请求不接受或持久化这两个字段。

候选接口只返回当前可用来源。用户保存新模型列表时继续执行现有权限和模型可用性校验。

### 网关行为

`/v1/models` 继续仅返回可调度模型。直接请求失效映射继续失败，不增加自动回退或自动改绑，确保来源分组与计费规则保持确定性。

## 前端设计

自定义分组管理弹窗中：

- 已失效的映射仍显示在所属模型列表中。
- 使用红色状态标识“来源分组已下架”或“已无权使用”。
- 失效项不能按原配置直接保存；用户需删除该项或从候选列表重新选择来源。
- 保存前给出明确提示和失效项数量。
- 桌面端与移动端沿用现有弹窗和折叠布局，不新增页面或左侧菜单。

## 现有线上数据

不删除、不自动迁移现有 29 条映射。新版本上线后这些映射会在界面中显式标红，用户可以重新选择来源。管理员另外保留只读受影响清单，用于后续按业务价格和权限人工确认迁移目标。

## 错误处理与兼容性

- 新字段为只读可选字段，旧前端可忽略，满足蓝绿部署兼容。
- 新前端在旧后端缺少字段时按可用处理，避免部署切换期间误标。
- 删除冲突使用新的稳定错误码，不复用通用数据库错误。
- 不新增数据库列或迁移，状态实时由来源分组计算。

## 测试

1. Repository：正确统计有效自定义分组对来源分组的引用，忽略已删除自定义分组。
2. Service：被引用来源返回 409 业务错误；无引用时保持原删除行为。
3. Service/handler：列表和详情保留失效模型并返回状态；正常模型保持兼容。
4. 网关：失效来源不进入模型列表且不能解析调用。
5. Frontend：失效标识、保存阻止、重新选择、移动端布局和旧后端兼容。
6. 回归：自定义别名、计费、API 密钥绑定以及普通分组管理测试保持通过。
