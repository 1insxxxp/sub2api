# 空回申请审核信息完善设计

## 背景

当前管理员在“空回申请”列表和审批弹窗中只能看到模型、用户、预计补偿金额及少量结构化证据。历史请求缺少响应证据时，管理员无法结合用量、费用、请求时间和上游状态做出可追溯的审核决定；批量审批也需要保证每条记录独立判定、失败不影响其他记录。

## 目标

- 在现有“使用记录 → 空回申请”页内提供完整、隐私安全的审批上下文。
- 桌面端使用宽弹窗，移动端使用底部面板，单条审批时无需跳转页面。
- 支持按选中记录批量批准或拒绝，并返回逐条成功/失败结果。
- 明确自动补偿与人工审批的来源，避免把两者混为一谈。
- 不读取、保存或展示请求正文和响应正文。

## 设计方案

### 后端数据

在管理员空回申请列表接口的 DTO 中补充来自 `usage_logs` 的非敏感字段：

- 请求时间、请求 ID、用量记录 ID
- 输入/输出/缓存 Token、原始费用、已补偿费用、计费类型
- 请求端点、上游端点、请求类型、流式标记、耗时、首 Token 时间
- 模型、分组、上游账号（现有字段保留）

继续返回现有结构化响应证据：HTTP/上游状态、文本/工具/推理/媒体标记、输出字节、事件数、结束原因、断开来源、上游错误类型、采集器版本。不得返回 prompt、response text 或原始请求体。

新增只读的补偿来源字段：

- `automatic`：规则判定批准并直接补偿，`reviewed_by` 为空
- `manual`：管理员批准后补偿，`reviewed_by` 有值
- `none`：未补偿或被拒绝

### 审批交互

- 列表继续展示状态、原因、估算补偿和证据摘要。
- 审批弹窗升级为桌面宽弹窗/移动底部面板，分成“申请信息、用量与计费、结构化证据、审核操作”四块。
- `missing_evidence` 显示醒目的“缺少服务端证据，只能人工判断”提示。
- 允许从弹窗打开已筛选的原用量记录或关联错误记录；仍不显示正文。
- 拒绝必须填写原因；批准备注可选。

### 批量审批

- 列表复选框选择记录后显示“批量批准”和“批量拒绝”。
- 批量操作前显示选中数量、预计总补偿金额和不可操作状态数量。
- 后端逐条执行已有审核/补偿事务；单条失败不回滚其他成功项。
- 返回 `succeeded`、`failed` 及失败原因，前端刷新列表和统计卡片，并保留失败项的选择状态。
- 批量拒绝仍要求统一填写拒绝原因；批量批准可填写统一备注。

## 隐私与安全

- 所有新增字段均为结构化元数据，不包含正文、提示词、响应内容或完整 API 密钥。
- 后端继续执行管理员权限校验、状态机校验、重复补偿幂等校验和金额事务校验。
- 批量接口限制单次最多 100 条，并拒绝非法状态或重复处理。

## 测试范围

- 后端 DTO/查询测试：新增字段映射、隐私字段不出现在响应中、补偿来源判定。
- 后端批量服务测试：部分成功、部分失败、重复处理、金额与状态一致性。
- 前端组件测试：审批弹窗展示完整信息、缺失证据提示、移动端布局、批量选择和结果提示。
- 运行相关 Go 单元测试、前端组件测试、前端构建和本地接口链路验证。
