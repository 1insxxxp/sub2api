# 抽奖次数按最近活跃用户发放设计

## 背景

管理员当前只能向指定用户或全部未删除用户发放抽奖次数。需要增加按用户最近 API 调用记录筛选的目标人群，用于向最近 7 天或最近 30 天内有过任意调用的活跃用户发放次数。

“有调用”只以 `usage_logs` 中是否存在该用户的调用记录为准，不区分请求成功、失败或是否产生费用。时间窗口按服务器当前时间向前回溯，使用 `usage_logs.created_at` 判断。

## 目标与非目标

### 目标

- 在管理员抽奖页面增加“最近活跃用户”发放目标。
- 支持最近 7 天和最近 30 天两个窗口。
- 发放前显示当前窗口内匹配的用户数量，避免管理员误发。
- 后端在事务内重新解析目标用户，确保预览与实际发放之间不会绕过软删除和活跃条件。
- 保留现有“指定用户”和“全部未删除用户”请求格式与行为，兼容旧客户端。

### 非目标

- 不引入自定义日期范围、按调用次数、按模型或按调用结果筛选。
- 不改变抽奖钱包、签到奖励或发放幂等逻辑。
- 不保存一份独立的“活跃用户名单”；每次预览和发放都实时查询调用记录。

## 方案

### API 契约

在管理员抽奖次数请求中增加目标类型和活跃窗口字段：

```json
{
  "target": "active",
  "active_days": 7,
  "amount": 2,
  "description": "活跃用户奖励",
  "request_key": "..."
}
```

目标类型为 `selected`、`all` 或 `active`。`selected` 继续使用 `user_ids`，`all` 继续支持现有 `all: true`；服务层将旧字段归一化为对应目标类型。`active` 要求 `active_days` 为 7 或 30，且不能同时提供 `user_ids` 或 `all: true`。

新增预览接口 `POST /api/v1/admin/lottery/attempts/preview`，复用目标字段并返回：

```json
{ "target": "active", "active_days": 7 }
```

响应返回匹配的非删除用户数量（以及可选的少量示例用户信息），不写入钱包或审计表。实际发放接口仍在事务中按相同条件查询用户 ID，避免仅依赖预览结果。

### 数据查询

活跃用户查询使用 `users.deleted_at IS NULL`，并通过 `EXISTS`/连接条件匹配：

```sql
EXISTS (
  SELECT 1 FROM usage_logs
  WHERE usage_logs.user_id = users.id
    AND usage_logs.created_at >= :since
)
```

现有 `(user_id, created_at)` 索引可支持该查询。查询结果按用户 ID 排序后进入现有批量发放流程，并继续受 `LotteryAttemptGrantMaxUsers` 限制；超出上限时返回明确的“目标用户过多”错误，不进行部分发放。

### 前端交互

- 发放目标单选项增加“最近活跃用户”。
- 选中后显示窗口下拉框（最近 7 天 / 最近 30 天）。
- 窗口改变时调用预览接口，显示“将向 N 位用户发放”。加载失败时禁止提交并展示错误。
- 提交时发送 `target`、`active_days` 及现有金额、备注、幂等键字段。
- 成功后清空预览状态、刷新次数余额列表并生成新的幂等键。
- 指定用户和全部用户的既有交互、校验和请求字段保持不变。

## 数据流与错误处理

1. 管理员选择“最近活跃用户”和时间窗口。
2. 前端调用预览接口，后端校验窗口并查询非删除用户数量。
3. 管理员提交发放请求。
4. 服务层校验目标、金额、备注和幂等键。
5. 仓储层在同一事务中解析活跃用户，创建每个用户的发放审计行、初始化/增加钱包余额并写入台账。
6. 任一用户写入失败则整个事务回滚；重复幂等键返回原始聚合结果。

窗口非法、目标字段冲突、没有匹配用户、目标用户超过上限等情况均返回现有统一错误响应，不创建任何钱包或台账记录。

## 测试策略

- 服务层：覆盖 active/7、active/30 的参数校验；非法窗口、混合目标、缺少目标的拒绝；预览和发放请求字段归一化。
- 仓储层：使用有调用、无调用、已软删除用户验证活跃用户解析；验证 7 天边界时间；验证超过上限时事务不产生部分记录；验证幂等重试。
- Handler/API：覆盖预览接口返回匹配数量、发放接口传递 active 条件，以及旧 `all`/`user_ids` 请求兼容。
- 前端：覆盖切换活跃目标、7/30 天预览请求、匹配人数展示、预览失败时阻止提交，以及提交 payload 包含 `target`/`active_days`。
